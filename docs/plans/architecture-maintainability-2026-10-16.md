# 架构低耦合与可维护性改善计划

- 日期：2026-10-16
- 状态：M0–M2 已实现；M3 本地验证完成，隔离 GUI 复测 BLOCKED（SSH 返回 `No route to host`）。未提交、未推送。
- 基线：`mygo` 分支，HEAD `0c3dbf7`，加当前未提交工作树。
- 目标：减少一次业务变化需要同步修改的入口，降低业务测试对真实文件、环境变量和全局状态的依赖。
- 范围：Gateway 编排、Provider 管理编排、跨入口契约与相关架构约束。不重做整套架构。

## 1. 决策与边界

保留现有 domain / usecase / adapters / bootstrap 结构，以已有模块承载改善，不新增通用 manager、facade、依赖注入容器或事件总线。

上一轮已经在工作树中完成的端口校验、非流式响应大小限制、架构 import 门禁，不重复实现。开始实施前应核对它们仍然存在，不将工作树内容误认为已提交版本。

本计划必须保持：

1. `config.json` 是配置事实，`models.json` 是显式发布结果；预览不能写入文件。
2. Gateway 发布保留冲突检查、文件锁、旧预览检测和原子写入；不把单文件写锁描述成跨文件事务。
3. Legacy 与 Native 的备份、版本前置条件、错误信封差异按现有合同保留。共享有效性规则不等于强制统一所有行为。
4. 保留凭据脱敏、凭据恢复、备份目录安全检查和取消语义。
5. 不迁移用户数据，不重置测试机，不覆盖现有无关修改，不升级依赖。

## 2. 执行顺序

| 阶段 | 优先级 | 交付物 | 前置条件 |
|---|---|---|---|
| M0：锁定行为合同 | P0 | 关键行为表、缺失的最小回归测试 | 无 |
| M1：集中 Gateway 编排 | P1 | 共享预览流程、完整迁移真实入口 | M0 的 Gateway 合同 |
| M2：解耦 Provider 管理编排 | P1 | 显式依赖与 Context、保留错误映射 | M0 的 Provider 合同 |
| M3：收口与验收 | P2 | 删除已替代编排、定向检查、证据记录 | M1、M2 |

按顺序实施，每个阶段形成可单独审查的改动。M1 若过大，可拆为“共享实现与测试”“入口迁移与旧实现删除”，但不能停留在两套业务编排长期并存的状态。

## 3. M0：先锁定行为，不再用目录结构代替合同

### 工作

- 核对当前工作树，区分用户已有修改、上一轮修复、本计划新增修改。
- 定位实际调用者、测试和动态引用，不因为名称带 `Legacy` 就删除。
- 在已有测试附近补缺口；已有有效测试直接复用，不另造通用测试框架。
- 为下面的差异建立明确断言；不预设各入口的错误状态码必须相同。

| 行为 | 必须一致的内容 | 必须保留或先核实的差异 |
|---|---|---|
| Provider 保存/重命名 | 校验、凭据处理、相关引用更新 | Native revision/备份与 Legacy 写入合同 |
| Provider 删除/复制/选中 | 不破坏其他配置、稳定的错误类别 | 不存在对象的处理、备份、幂等性 |
| Gateway generated/draft/selected 预览 | 同一输入产生相同核心计划、无写入 | DTO、排序展示、提示文字 |
| Gateway 发布 | 冲突不写入、并发变化不被静默覆盖 | 各入口何时重新生成计划、如何确认发布 |
| Settings | 共享有效性规则 | Legacy 无备份、Native revision；JSON 默认化 |
| 取消/存储失败 | 不谎报成功、不产生半写入 | UI 可读错误与 HTTP 错误信封 |

### 验收

- 每项涉及的现有测试有明确位置；缺失项补测试，不把整段被 `t.Skip` 的测试计为覆盖。
- 后续实现前，针对要改变的耦合点建立可运行的测试。例如：内存依赖能够生成 Gateway 预览，Provider 管理操作能够注入失败而不创建真实配置文件。
- 不要求在本阶段执行全仓库测试，也不修改无关旧测试。

## 4. M1：集中 Gateway 预览编排

### 现状与改动目标

目前 HTTP、CLI、Native Gateway 与 Native JSON 编辑入口分别处理读取配置、读取当前发布状态、选择计划构建方式的流程。业务计算已共享，但调用者仍需要理解流程顺序。

目标是让调用者提交生成、草稿或选择意图，取得可展示及可发布的计划；配置读取、当前状态读取、catalog 获取与计划构建由共享用例协调。

### 文件范围

- `internal/usecase/gateway/service.go` 及相关测试。
- `internal/bootstrap/gateway.go`；仅在需要满足最小读取接口时修改现有 outbound 实现。
- `internal/server/gateway_handlers.go`。
- `cmd/pi-switch/main.go` 中 Gateway 命令。
- `desktop/native_gateway.go`、`desktop/native_json.go`。
- `internal/gateway/gateway.go`、`internal/gateway/enrich.go`：核对兼容调用，不自动删除。

### 实施要求

1. 在现有 Gateway 用例内收拢编排，复用现有 Store、Catalog、domain 计划函数；配置读取通过消费者需要的最小接口传入。
2. generated、draft、selected 保持显式意图。不要以多个布尔参数、字符串模式或空值组合制造新的隐式协议。
3. 保留已有 `CanonicalGatewayPlan` 与选择类型。仅对稳定操作输入/结果收紧类型；JSON 编辑区域继续允许动态 JSON，不进行全项目 map 到 struct 的转换。
4. 同步迁移上述入口。入口保留请求解码、展示转换、确认交互及错误信封；移除被共享用例替代的重复读取和流程选择。
5. 发布仍经现有 Publish 和文件 adapter，不绕开 stale 检查。不改变“发布时重建计划”或“发布确认过的计划”的入口合同；如发现合同不一致影响正确性，单独记录并决策，不偷偷统一。
6. 无生产调用的旧方法在确认测试、兼容引用后删除；仍有兼容调用的保留窄转接，不保留第二套编排实现。

### 验收

- generated/draft/selected 主路径可用内存实现测试，无真实 HOME、数据库或网络依赖。
- 计划构建顺序只在共享用例中维护，迁移入口不再自行拼接同一流程。
- nil 选择与显式空选择、无变更、冲突、catalog 失败/告警、读取失败、取消均有匹配现有语义的测试。
- 预览不写入；发布仍保留原有锁、原子性和旧状态检查。
- HTTP/CLI/Native JSON/Native Gateway 都完成直接影响范围的验证，不能只迁移 GUI 页面。

## 5. M2：让 Provider 管理编排接受依赖与 Context

### 首批范围

只处理 `SaveProvider`、`DeleteProvider`、`SetCurrentProfile`、`DuplicateProvider` 及直接调用链。它们聚合了共享业务调用与兼容错误映射，适合作为第一批可独立验证的改善。

涉及 `internal/application/management.go`、`provider_operations.go`、现有 Provider 用例及真实入口调用者。实施时先检索完整调用集，再修改签名。

### 实施要求

1. 保留现有领域规则和用例，不再创建另一份 Provider 业务实现。
2. 管理编排接受所需的 Provider 用例依赖；已有具体类型足够时直接使用，只有测试或实现替换确有需要时才引入最小接口。
3. 从 HTTP 请求或 Native 任务传入 Context，不在可取消操作内部重新用 `context.Background()` 截断取消链。同步 CLI 可在最外层创建 Context。
4. 保留 UI 可读错误、错误类别映射、脱敏、备份和 revision 语义。
5. 装配留在真实入口：利用现有 bootstrap 创建用例，再交给 application。只要 application 包仍导入 bootstrap，就不能让 bootstrap 反向导入 application 造成包循环。
6. 迁移后的核心编排函数不自行创建文件 adapter 或调用 bootstrap。旧公开入口若无兼容调用则删除；若必须保留，只作薄兼容转接，不扩展其职责。

### 验收

- 四类操作可以注入成功、revision 冲突、校验失败、持久化失败和取消结果，测试无需真实配置文件。
- 文件锁、原子写入、备份安全仍由原有存储集成测试负责，不用假实现替代这些检查。
- 取消不被转换为成功；存储失败不被吞掉；凭据不进入面向用户的错误文本。
- Native 与 Legacy 的差异保持显式，不增加到处传递的 `legacy` 开关。

### 明确暂缓

配置恢复/全量替换的依赖重整不混入本批。它们包含安全校验、锁内版本比较和备份时序，不能为了统一构造方式草率搬动。若后续继续改善，单独制定存储事务接口与故障测试后再实施，不将其标记为本计划已解决。

## 6. M3：删除重复实现并完成定向验收

### 收口

- 搜索迁移后的旧函数、编排片段和引用，删除确实被替代的内容，不仅新增一层转发。
- 更新 `docs/architecture.md` 的真实调用链和兼容说明。
- 不增加未经触碰的模块约束。架构检查仍只证明直接 import 规则，不代表已经消除所有隐式依赖。
- 新增核心测试优先使用显式依赖；不新增通过修改全局环境或 `store.ResetForTest` 驱动纯业务测试的路径。

### 验证方式

按阶段选择相关检查，已通过且未受后续修改影响的检查不重复执行：

- Gateway：`internal/usecase/gateway`、`internal/domain/gateway`、`internal/adapters/outbound/filegateway` 的相关测试。
- Provider：`internal/usecase/providers`、`internal/application` 的相关测试；持久化变化才补跑对应 fileconfig 检查。
- 入口：先定位已有 Test 名称，再用 `-run` 执行 HTTP、CLI 和 Desktop 的受影响测试；新增用例必须确认实际执行，不能接受零测试匹配。
- 依赖方向：`go run ./internal/archcheck`，检查器本身变化时再跑其测试。
- 静态检查：相关包的 `go vet`、格式与相关 diff 检查。
- Desktop：沿用现有 `CGO_ENABLED=0 go test -mod=readonly` 方式执行定向测试；若改变任务取消或确认交互，再安排隔离 GUI 场景验证，不将编译通过视为交互通过。

## 7. 不做什么，以及如何控制风险

- 不全量搬迁 `internal/server`，不按文件行数拆包，不更换框架或数据库。
- 不仅因为一个接口只有一个实现就删除它，也不为将来可能需要的实现预建接口。
- 不重写全局数据库生命周期，不建设多配置、多租户或插件系统；当前单机运行前提不变。
- 不顺手修复无关历史问题；新发现先独立记录并说明是否阻塞本阶段。
- 不自动提交或推送。需要提交时，仅包含本阶段相关修改。
- 某阶段失败时，停止依赖它的后续阶段，只撤销能明确归属于本阶段的修改；不得使用整树 reset/checkout 覆盖用户数据或无关工作。

成功标准不是目录变多或接口变多，而是：Gateway 流程变化只需修改共享编排，Provider 管理行为可以不依赖真实文件独立验证，并且原有兼容与安全约束不退化。
